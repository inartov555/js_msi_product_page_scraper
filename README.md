# MSI Catalog Scraper

JavaScript + Node.js + Playwright scraper for the MSI US Store. It supports single-product scraping, full catalog crawling, local search, and product comparison.

## Requirements

- Docker

## Commands

Start with Docker

```bash
./run_scraper.sh crawl --refresh false
./run_scraper.sh scrape https://us-store.msi.com/Desktops/Vision-ZS-9NVV-2080US
./run_scraper.sh compare "MAG Z890 TOMAHAWK WIFI" "PRO Z890-P WIFI"  # collect data of a product
./run_scraper.sh search "Motherboards"
./run_scraper.sh serve  # Scraper service with APIs
./run_scraper.sh test:unit  # only unit tests
./run_scraper.sh test:e2e   # only end-to-end tests
./run_scraper.sh test:all   # all available tests
```

## Changes

- **Concurrent category discovery**
  Multiple product categories can be scanned in parallel while pagination inside each category remains sequential and predictable.

- **Non-blocking retries**
  Temporary failures such as HTTP 403/429/5xx can be retried without blocking other concurrent discovery work.

- **Configurable browser profiles**
  The scraper can use deterministic desktop browser profiles with consistent headers and context settings.

- **Separate unit and E2E test suites**
  Unit tests and end-to-end tests can be run independently, or together with `test:all`.

- **Reliable CI environment setup**
  The project can initialize its environment from `env.example` when `.env` is not present.

- **Docker-compatible output generation**
  Scraper commands can write generated files to the host-mounted `output/` directory in CI and local Docker runs.

- **Correct command failure reporting**
  `run_sraper.sh` returns the actual container exit code, so failed scraper commands are reported correctly to CI and callers.

- **Persistent test outputs**
  Files generated by E2E tests remain available in `output/` after `test:all` completes.

- **Fresh-output E2E validation**
  E2E tests remove the target artifact before each command so they verify that the command really generates a new file.

- **API health and behavior testing**
  The E2E suite verifies health, product search, comparison, invalid input handling, missing products, and unknown routes.

- **Fast API startup failure detection**
  API E2E tests stop immediately when the server process exits instead of waiting for the full timeout.

- **Live API/server logs during tests**
  Server stdout and stderr can be printed live while still being captured for assertions.

- **Safer retry behavior for product scraping**
  Unknown application or extraction errors are not automatically treated as transient network failures.

- **Cleaner CLI behavior**
  Unsupported `--json` functionality is no longer advertised in the CLI help.

## Catalog

The full catalog is stored in:

```text
output/catalog.json
```

Comparison tables are saved to:

```text
output/comparison.csv
```

Search results are saved to:

```text
output/search.csv
```

A single scraped product is stored by default in:

```text
output/single-product.json
```

The `output` directory is mounted into the container so the catalog persists between runs.

The `serve` command starts the Dockerized API. The end-to-end serve test checks `/health`, `/products`, `/compare`, validation errors, unknown products, and unknown routes. Docker Compose is required.
The API exposes the `/health`, `/products`, and `/compare` endpoints from `src/server.js`.
